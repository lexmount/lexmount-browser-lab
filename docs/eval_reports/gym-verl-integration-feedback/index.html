NeMo-Gym × verl 集成:一线使用反馈与建议

基于 WebVoyager 浏览器 RL 场景的数月实际使用:昇腾 910B 与 A100 双栈、 多次 60 步受控全量训练、单日 1.3 万个远端浏览器 session。 每条建议都附我们踩坑的实测数字与建议的具体接口形态。

总评:集成路径已跑通规模化训练,异步 rollout 与 verifier 设计好评;八项建议集中在资源生命周期与训练信号质量两大类

  • 可用性:V1 TaskRunner + TransferQueue 的异步 rollout 与远端环境天然契合,4 小时级长跑零崩溃
  • 最痛的点:环境资源生命周期缺一等公民钩子——我们自建审计后才做到 13,160 session 零泄漏
  • 其次:环境基建失败缺协议级语义(现状只能 reward=0),需要 environment_invalid 字段 + 组级重采 API
  • 可观测性:rollout ↔ 环境 ↔ 远端资源三方 id 断裂,靠自研埋点才 join 上(6,695 / 6,695)

1 · 我们的集成形态

训练侧 verl GRPO(TaskRunnerV1 + TransferQueue,vLLM 生成,DAPO + 动态采样); 环境侧 NeMo-Gym server 承载 WebVoyager 浏览器环境(工具循环 act/observe, OpenAI 兼容 judge);浏览器本体在远端平台,每个 session 一个独立 pod, 平台侧 Prometheus 按 session 出资源 series。

规模背书:此形态下完成多次 60 步全量训练(8 任务 × 8 rollout / 步), A100 单日双跑共 13,160 个远端 session,4 小时级长跑零崩溃、零人工干预。

2 · 资源与生命周期:最需要一等公民支持的地方

浏览器 RL 的环境资源(远端 session)有真实成本。verl 侧的中断、重试、步内异常 都可能让环境的 close 调用永远不会发生;协议目前没有任何兜底。

建议 1 · 生命周期钩子(协议级)

# 环境基类(建议增加,由框架保证必达)
class Env:
    def on_rollout_abort(self, rollout_id, reason): ...  # 超时/重试/取消时
    def on_run_exit(self): ...                           # 进程退出兜底
# server 侧:session registry + TTL 自动回收 + create/close 配对指标

建议 2 · 并发背压做进框架

浏览器类环境的瓶颈在远端配额而非 GPU(我们实测加卡无收益)。session create 突发会打崩远端调度,我们手动限制 create 并发 16、总并发 64 才稳定。 建议 Gym client 内置 per-resource 限流配置(create 速率、最大并发、指数退避), 而不是每个环境自己实现。

建议 3 · session 池化 / 预热语义

create 中位 4.45 s,约占 rollout 端到端(32.5 s)的 14%;远端冷启动高峰期 我们观测到过 30 s 级中位。建议协议支持 session 复用或预建池: trainer 声明下一批需求量,server 提前建好。这部分墙钟是纯浪费。

3 · 训练信号质量:环境失效需要协议级语义

建议 4 · rollout 返回结构(具体字段)

{
  "reward": 0.0,
  "environment_invalid": true,            # 与 reward 正交
  "invalid_reason": "navigate_timeout",   # 枚举:infra/tool/close_rpc/...
  "resource_ids": {"browser_session": "session_1755..."},  # 见 §4
  "stage_timing_s": {"create": 4.4, "act": 3.1, "observe": 0.2,
                      "judge": 2.3, "cleanup": 1.6}          # 见 §4
}

建议 5 · 组级补采一等 API

# 现状:trainer 裸循环调环境,组审计逻辑全部自研
# 建议:
groups = gym.rollout_groups(
    prompts, group_size=8,
    min_signal_groups=8,      # 有效且 reward std>0 的组数下限
    max_resample_rounds=2)    # 墙钟保护

DAPO 动态过滤要求"补采到足够多有信号的组"。这个循环跨 Gym 边界串行执行, 墙钟膨胀且各家重复造轮子;做成 server 侧原语后可以并行补采。

4 · 可观测性:让三方数据默认可 join

本次引擎对比报告的每个远端数字,都依赖"训练 rollout ↔ 环境 session ↔ 平台资源" 三方精确关联。现状协议里这条链是断的(图 1-1),我们的做法值得标准化:

建议字段方向作用
rollout_idtrainer → env,全链路透传环境日志、judge 调用、资源事件都可归属到具体 rollout 与训练 step
resource_ids{}env → trainer,随返回回填与平台监控(Prometheus label)join,资源成本可按 rollout 归因
stage_timing_s{}env → trainer,标准分段延迟create/act/observe/judge/cleanup 分段;定位瓶颈不再需要自研埋点
resource_eventsenv server 标准日志流create/close/delete 事件 + 时间戳,泄漏审计与配对计数的数据源

为什么值得:我们靠等价自研机制,才能给出"chrome 组 6,695 个 session 与审计清单 100% 匹配、外来 16 个 session 被识别剔除"这种粒度的报告。 有标准字段后,任何接入 Gym 的环境都自动获得这个能力。

5 · 工程接口:定制点靠 fork 太脆

为接入浏览器环境,我们最初 fork 了 4 处 verl 核心组件;verl API 迭代快, 只能 pin 死 commit(30119a2)。后来全部改写为 "注册 + 运行时 patch"才敢跟随上游升级。

建议 6 · 为 runner / worker / rollout loop 提供稳定的 plugin & registry 接口(入口点注册自定义实现),让 recipe 不改 core 源码。 判据很简单:一个新环境接入,应该只新增文件、不修改 verl 本体。

6 · 做得好的部分

· OpenAI 兼容 verifier(judge)模式:我们把判分模型当成普通 endpoint 挂进去,零适配成本,换 judge 模型只改一个 URL。
· V1 TaskRunner + TransferQueue 异步 rollout:与高延迟远端环境天然契合, 64 并发 rollout 打满远端配额,GPU 利用率均值 63% 且长跑稳定; 这套异步架构是浏览器 RL 可行的前提,请保持。
· 环境即 server 的边界划分:训练栈与环境解耦干净, 我们双引擎 A/B 只需要改一个环境参数,训练侧零改动——这正是本次对比实验能严格受控的原因。
