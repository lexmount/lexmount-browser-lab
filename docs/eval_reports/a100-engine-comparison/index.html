Lexmount 作为 RL 浏览器环境:与云端 Chrome 的受控全维度对比

同一台 A100×8、同一模型与训练配方、同一 session 池上限下,先后各跑 60 步 GRPO(DAPO + 动态采样),两组引擎版本均以 custom_image_id 固定。 本页只呈现该设置下的测量值;所有数字保留分母、时间窗与过滤条件,session 级数据可在 Prometheus 中逐条复核。

测量口径

训练侧逐 rollout 记录延迟分解与 reward(observability schema v2); 宿主侧以 5 秒间隔采样 GPU 利用率/显存/功耗、CPU、内存与网络, 统计窗按 session 活动窗裁剪(排除训练结束后的空转采样); 远端侧每个浏览器 session 在 Prometheus 中是独立 pod series (label_session_id),训练栈将每次 create/close 写入审计文件, 两侧按 session id 精确 join。

观测事实:GPU 侧两组几乎不可区分(利用率、显存、功耗差均在噪声内)。 在 8×8 异步并发 + A100 生成速度下,环境不构成 GPU 瓶颈;两引擎对"训练机本身"的 开销同样接近零——这与本地 docker 方案(浏览器与训练争抢同机资源)形成架构性差异。 云端 chrome 组每有效 rollout 卡时略低,主要因其 invalid 率更低、有效样本分母更大。

5 · 训练收益:两种引擎均正常收敛

同一配方在两种引擎上各跑 60 步,reward 曲线形态一致、均稳定上升, 60 步总时长相近(4.37 vs 4.15 h)——切换引擎不改变训练的可用性与节奏。

观测事实:两种引擎下 GRPO 训练均获得清晰的正向学习信号, 分组审计 60/60 步全部通过。环境选择不构成训练收益的瓶颈; 各引擎仅单次运行,故本报告不比较两组 reward 的绝对差距。
