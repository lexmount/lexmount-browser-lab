1 · 背景与读者问题

NeMo-Gym 生态目前缺一个可规模化的浏览器环境。要说服训练侧采用 Lexmount Browser,需要回答的不是"它能不能跑",而是三个可测量的问题: 在相同训练配置下收益是否一致;在等量并发下环境延迟与资源成本 是多少;长时间训练中失败模式是否可控。

此前在 910B 上已完成三消融(GRPO 基线 → +DAPO → +动态采样)并确认最终配方。 本报告在 GPU(A100)上以该配方做双引擎受控对比:lightmount(自研轻量引擎) 与 lexmount normal(云端 Chrome)。二者走完全相同的 CDP 通路与训练栈,唯一差异是 browser_mode 一个参数;两组引擎镜像均通过 custom_image_id 固定版本,排除平台默认镜像滚动带来的漂移。

3 · 功能对比:先回答"能不能",再比"快不快"

三种把浏览器接进 RL 训练的方式,能力边界不同。性能数字只在能力等价的前提下才有意义, 因此先给定性对照。

本地 docker Chrome 一列为架构性事实与公开常识,本轮未实测(见 §9)。

观测事实:同配置下 lightmount 组的 reward 全程高于 chrome 组 (全程均值 0.355 vs 0.221),而墙钟基本相当(chrome 略快 5%,部分来自其平均 响应序列更短:3,510 vs 3,641 字符中位)。

各引擎仅一次 60 步运行、同一数据顺序、无多种子重复,reward 差距不能排除 单次运行方差与页面内容随时间变化的贡献;§8 的 invalid 率差异(两组任务有效样本构成不同)也可能影响 学习信号。把该差距解读为"lightmount 必然训得更好"超出本轮证据边界;结论以资源与延迟维度为主。

5 · 速度:rollout 延迟逐段分解

端到端时延由五段构成:session 创建 → 交互(act)→ 观测(observe)→ 判分 → 清理。 逐段对比才能定位差异来自引擎还是栈。

观测事实:A100 窗口下两引擎端到端中位基本持平(32.5 vs 31.9 s)。 结构上 chrome 的 act/observe 略快、清理慢 3.5 倍(5.58 vs 1.60 s); lightmount 的 P95 尾部更差(81.6 vs 58.4 s),与 §8 的导航超时集中一致。

910B 窗口(2026-08-07/08,旧采集版本)曾测得 lightmount 端到端中位快 22% (75.3 vs 103.7 s)。两轮结论不同,可能来自引擎版本、远端集群负载或站点内容随时间的变化; 以本轮 pin 版本、串行同日的测量为准。

lightmount 的 invalid 率(8.5%)约为 chrome 的 2 倍,集中在导航超时与 close RPC 失败两类。归因未完成:导航超时阈值按 Chrome 语义设定,可能不适配 lightmount 的加载 事件时序;close RPC 失败(148 例)是本轮新出现的类别,需要引擎侧日志定位。 在归因结论出来前,本报告不把稳定性写成 lightmount 的优势项; 但两类失败均被训练栈正确识别、隔离并重采,未污染训练信号,也未造成泄漏。

9 · 限制与未验证项

· 单机单模型:结论覆盖 A100×8 + Qwen3-8B + WebVoyager 任务分布,未验证多机与更大模型。
· 每引擎一次 60 步运行,无多种子重复;§4 的 reward 差距按单次观测呈现,不外推为普适结论。
· 两个训练窗同日先后进行(间隔 10 分钟),共享公网与远端集群,潮汐负载未完全受控; per-session 单价与积分口径对此类漂移相对稳健。
· lightmount 为 2026-08-07 构建(老版,与此前所有实验一致);新版(moli 系列)就绪后 将以同口径重跑,验证版本演进的影响。
· 本地 docker Chrome 未实测,§3 中该列为架构性推断。
