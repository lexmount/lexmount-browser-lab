1 · 背景与读者问题

NeMo-Gym 生态目前缺一个可规模化的浏览器环境。要说服训练侧采用 Lexmount Browser,需要回答的不是"它能不能跑",而是三个可测量的问题: 在相同训练配置下收益是否一致;在等量并发下环境延迟与资源成本 是多少;长时间训练中失败模式是否可控。

本报告在 GPU(A100)上以既定配方(GRPO + DAPO + 动态采样)做双引擎受控对比:lexmount(自研轻量引擎) 与云端 Chrome。二者走完全相同的 CDP 通路与训练栈,唯一差异是 browser_mode 一个参数;两组引擎镜像均通过 custom_image_id 固定版本,排除平台默认镜像滚动带来的漂移。

3 · 功能对比:先回答"能不能",再比"快不快"

三种把浏览器接进 RL 训练的方式,能力边界不同。性能数字只在能力等价的前提下才有意义, 因此先给定性对照。

能力lexmount(远端自研)云端 chrome(远端)本地 docker Chrome
隔离模型session 级独立 pod池化 pod,分配制(label_browser_pool_role)与训练同机,抢 CPU/内存
版本固定custom_image_id 按 session 指定引擎构建,可复现自行管理镜像
Session API / 池化create/close/delete + 孤儿清扫,配额语义明确自行管理容器生命周期
协议标准 CDP websocket,栈零改动切换CDP(自建代理)
资源可观测per-session Prometheus series(本报告数据来源)需自建 cAdvisor 等
对训练机的资源占用≈0(远端承载;本轮实测训练机 CPU 均值 8.5%,全部来自训练本身)随并发线性增长,与 rollout 争核

本地 docker Chrome 一列为架构性事实与公开常识,本轮未实测。

这一节回答"换引擎是否改变训练结果、是否节省墙钟"。

观测事实:同配置下 lexmount 组的 reward 全程高于 云端 chrome 组 (全程均值 0.355 vs 0.221),而墙钟基本相当(云端 chrome 略快 5%,部分来自其平均 响应序列更短:3,510 vs 3,641 字符中位)。

各引擎仅一次 60 步运行、同一数据顺序、无多种子重复,reward 差距不能排除 单次运行方差与页面内容随时间变化的贡献;两组 invalid 率不同(有效样本构成不同)也可能影响 学习信号。把该差距解读为"lexmount 必然训得更好"超出本轮证据边界;结论以资源与延迟维度为主。

5 · 速度:rollout 延迟逐段分解

端到端时延由五段构成:session 创建 → 交互(act)→ 观测(observe)→ 判分 → 清理。 逐段对比才能定位差异来自引擎还是栈。

观测事实:A100 窗口下两引擎端到端中位基本持平(32.5 vs 31.9 s), 即换用 lexmount 不付出吞吐代价;其中 session 清理 lexmount 快 3.5 倍 (1.60 vs 5.58 s),其余各段差异均在秒级以内。

观测事实:GPU 侧两组几乎不可区分(利用率、显存、功耗差均在噪声内)。 在 8×8 异步并发 + A100 生成速度下,环境不构成 GPU 瓶颈;两引擎对"训练机本身"的 开销同样接近零——这与本地 docker 方案(浏览器与训练争抢同机资源)形成架构性差异。 云端 chrome 组每有效 rollout 卡时略低,主要因其 invalid 率更低、有效样本分母更大。
