1 · 背景与读者问题

NeMo-Gym 生态目前缺一个可规模化的浏览器环境。要说服训练侧采用 Lexmount Browser,需要回答的不是"它能不能跑",而是三个可测量的问题: 在相同训练配置下收益是否一致;在等量并发下环境延迟与资源成本 是多少;长时间训练中失败模式是否可控。

此前在 910B 上已完成三消融(GRPO 基线 → +DAPO → +动态采样)并确认最终配方。 本报告在 GPU(A100)上以该配方做双引擎受控对比:lightmount(自研轻量引擎) 与 lexmount normal(云端 Chrome)。二者走完全相同的 CDP 通路与训练栈,唯一差异是 browser_mode 一个参数。

3 · 功能对比:先回答"能不能",再比"快不快"

三种把浏览器接进 RL 训练的方式,能力边界不同。性能数字只在能力等价的前提下才有意义, 因此先给定性对照。

能力lightmount(远端自研)lexmount chrome(远端)本地 docker Chrome
隔离模型session 级独立 pod池化 pod,分配制与训练同机,抢 CPU/内存
并发弹性⟦占位:配额/伸缩语义⟧⟦占位⟧受单机资源硬限
Session API / 池化create/close/delete + 孤儿清扫,配额语义明确自行管理容器生命周期
协议标准 CDP websocket,栈零改动切换CDP(自建代理)
资源可观测per-session Prometheus series需自建 cAdvisor 等
对训练机的资源占用≈0(远端承载)随并发线性增长,与 rollout 争核

本地 docker Chrome 一列为架构性事实与公开常识,本轮未实测(见 §9)。

lightmount 的 invalid 率(A100 7.8%,910B 3.7%)高于 chrome(910B 0.85%), 集中在导航超时。归因未完成:可能是超时阈值按 Chrome 语义设定,也可能是特定站点渲染路径差异。 在归因结论出来前,本报告不把稳定性写成 lightmount 的优势项。

9 · 限制与未验证项

· 单机单模型:结论覆盖 A100×8 + Qwen3-8B + WebVoyager 任务分布,未验证多机与更大模型。
· lightmount 全量跑早于 session id 埋点上线,其远端数据按 mode+project+时间窗过滤; 新版 lightmount 发布后将带埋点重跑,得到与 chrome 完全对称的 session 级清单。
· 本地 docker Chrome 未实测,§3 中该列为架构性推断。
· 两个 60 步窗相隔一天,共享公网与远端集群,潮汐负载未受控; 并发单价指标(per-session)对这类漂移相对稳健。
